How Seamless Context Routing Works

No @agent call needed. Claude Code always loads CLAUDE.md and ~/.claude/rules/agent-routing.md at every session start. When you type a message, the routing rules match trigger phrases and automatically activate the right agent and skill — before you finish the thought.

Dev Team — Daily Loop

The dev team runs a daily cycle, not a weekly one. PM kicks off every morning, waits for human input, auto-approves P0 items after 2 hours if no human responds, then hands to the developer who implements and knows when to call QA based on its own skills. The cycle ends with a clean merged PR.

Product Manager

Plans work, owns epics, runs standups, and keeps the team unblocked — without writing code.

~/.claude/agents/product-manager.md · agents/product-manager/context/
Daily Routine
08:00 — Run standup
Reads git log --oneline -10 + epic-status.md. Compiles status into daily briefing.
→ pm-standup
Update project-status.html
Reflects current sprint state: in-progress, blocked, done. Single-file dashboard opened in browser.
→ pm-project-status
Flag P0 items + notify via Lark
Sends Lark message with today's P0s needing human decision. Waits 2hrs.
10:10 — Auto-approve P0 (if no human input)
Creates GitHub Issues for approved P0 items and assigns to developer.
→ pm-to-issues
Fri 16:00 — Weekly retro
Reads this week's git history. Updates epic-status.md. Plans next week's content topic for marketing.
Hard Rules
✗Never approves implementation without a written reviewed plan.
✗Never creates issues without grilling the plan first. pm-grill-with-docs runs before pm-to-issues.
✗Always reads git log before every task. Never assumes state from memory.
✗Never skips the 2hr human window. Auto-approve only fires at 10:10 with zero human response.
Output Paths
→docs/product/epics.md
→docs/product/epic-status.md
→docs/project-status.html
→GitHub Issues (gh issue create)
→Lark notifications
Skills
pm-standup
Compiles daily standup from git log + epic-status.md into a human-readable briefing.
Reads git log → identifies completed/blocked items → writes standup/{date}.md → sends Lark summary.
pm-grill-with-docs
Validates a draft plan against live project docs before approval. Blocks plans that conflict with epics or in-progress work.
Reads project-status.html + epics.md + epic-status.md → cross-references plan → generates 5–10 specific questions → issues APPROVED / REVISE / BLOCKED verdict.
pm-to-issues
Breaks an approved spec into vertical-slice GitHub Issues that a developer can pick up independently.
Identifies user-visible slices (not horizontal layers) → writes each as a gh issue with acceptance criteria → runs gh issue create → updates epic-status.md with issue numbers.
pm-epic-writing
Writes a full epic document with scope, acceptance criteria, out-of-scope list, and effort estimate.
Prompts for business goal → writes epic in docs/product/epics.md format → appends to epic-status.md as "planned".
pm-project-status
Updates the project-status.html single-file dashboard with current sprint state.
Reads git log + epic-status.md → updates in-progress table, blocked items, done items → rewrites the HTML dashboard file.
pm-client-interview
Structured discovery interview to extract business context, goals, constraints, and success metrics from a new client.
Runs through 5 question categories → records answers → writes context/client-brief.md → seeds initial epics.
pm-documentation
Updates project documentation — architecture docs, decision records, and engineering change logs.
Identifies which docs need updating → reads current version → writes delta → commits to docs/ with clear commit message.

Developer

Implements approved plans, debugs bugs, and hands off to QA — never starts without a PM issue.

~/.claude/agents/developer.md · agents/developer/context/
Daily Routine (in the dev loop)
Pick up approved PM issue
Reads git log first. Identifies what's already done and what's next.
Zoom out (if unfamiliar module)
Maps exports, callers, data flow, invariants before touching code.
→ dev-zoom-out
Stress-test the plan
10+ adversarial questions before writing code. Blocks on unanswered questions.
→ dev-grill
Implement (with TDD if required)
Vertical slices only. Red → green → refactor. No horizontal layers.
→ dev-tdd
Know when to call QA
Uses dev-qa-delegation skill to decide: too early wastes QA time, too late risks regressions.
→ dev-qa-delegation
Open PR + notify + trigger QA
Writes HANDOFF.md, opens GitHub PR, emails human, triggers QA review agent.
→ dev-handoff
Hard Rules
✗Never starts without an approved PM issue.
✗Never force-pushes or skips CI.
✗Never merges its own PR.
✗Runs dev-zoom-out before touching unfamiliar modules.
✗Always reads git log -10 before starting.
Output Paths
→Feature branches → PRs
→docs/engineering/changes/{date}-{slug}/HANDOFF.md
Skills
dev-diagnose
Structured debug loop for bugs with non-obvious causes.
Reproduce → minimise → hypothesise (3–5 theories) → instrument one at a time → fix minimal root cause → gate (all tests pass, logs removed).
dev-zoom-out
Produces a 1-page module summary before making changes in unfamiliar territory.
Maps public surface → finds callers (grep) → traces data flow → identifies invariants → writes MODULE / ENTRY POINTS / DANGER ZONES summary.
dev-grill
Adversarial plan interrogation — 10+ questions across scope, data, errors, testing, deployment, and assumptions.
Generates questions → requires answers → marks unanswered as blockers → issues APPROVED / BLOCKED verdict. No code before APPROVED.
dev-tdd
Enforces strict red-green-refactor discipline with vertical slices only.
Failing test first → minimum code to pass → refactor with tests green → commit test then impl → next slice. Horizontal slicing is banned.
dev-prototype
Throwaway spike to answer one specific technical question — then delete the code.
Define the exact question → set timebox (max 2h) → build minimum to answer → record QUESTION / ANSWER / EVIDENCE / IMPLICATIONS → delete all prototype code.
dev-handoff
Session/agent handoff documentation so the next session or QA agent can continue without context loss.
Writes HANDOFF.md to docs/engineering/changes/{date}-{slug}/ with: what's done, in progress, blocked, files changed, how to test, open questions. Commits + sends Lark.
dev-improve-arch
Strategic module improvement — friction inventory → ranked improvements → one approved change at a time.
Domain scan (no judgment) → list friction items (type + impact + effort) → compute Priority = (Impact×2) + (1/Effort) → propose highest-priority one → implement only after approval.
dev-planning
Implementation plan before coding — breaks down a PM issue into ordered steps with file-level detail.
Reads the GitHub Issue → breaks into ordered steps → estimates effort → confirms with PM before starting → creates TodoWrite checklist.
dev-qa-delegation
Decides when and how to hand off to QA — avoids premature or delayed QA calls.
Checks acceptance criteria coverage → runs local tests → if passing and ACs met → writes handoff doc → triggers QA review via RemoteTrigger or @qa tag.

QA

Classifies every bug, verifies acceptance criteria, and signs off PRs — never skips triage.

~/.claude/agents/qa.md · agents/qa/context/
Routines
Wed 14:00 — Regression check
After Web Publisher commits a new post, QA verifies the site renders correctly.
→ qa-best-practices
On PR open — PR review
Triggered by Developer via RemoteTrigger. Reviews PR against acceptance criteria.
→ qa-documentation
On bug report — Triage
Classify → score (severity × frequency × blast) → route. Always before fixing.
→ qa-triage
Hard Rules
✗Never skips triage. Every bug is classified and scored.
✗Never signs off without testing acceptance criteria from the PM plan.
✗Never marks a regression as P3 without PM review.
Output Paths
→docs/qa/{date}-{slug}-triage.md
→docs/qa/{date}-{slug}-qa-report.md
→docs/product/epic-status.md (known issues)
→docs/project-status.html (bugs table)
Skills
qa-triage
Bug triage state machine — classify, score priority, and route every bug before it's touched.
Classify as regression/new-defect/performance/ux-degradation/data-integrity/security → score Severity × Frequency × Blast (1–5 each) → map score to P0–P3 → route to correct agent → write triage report → update epic-status.md + project-status.html.
qa-best-practices
Defines the test strategy for a feature: what to test, how to test it, and what AI cannot test.
Maps feature scope → identifies test pyramid layers (unit/integration/e2e) → lists manual-only scenarios → writes test plan with specific commands.
qa-documentation
Writes a formal QA report for a completed feature or regression cycle.
Reads acceptance criteria → documents pass/fail per criterion → lists open bugs with triage scores → issues QA verdict (PASS / PASS WITH NOTES / FAIL).
qa-planning
Creates a full test plan for an epic or sprint before development begins.
Reads epic spec → maps all acceptance criteria → designs test cases per criterion → estimates QA effort → flags automation gaps.

Claude Code PreToolUse hooks that intercept and block dangerous git commands before they execute.

devops-ops
Operational runbook: deploy health check, rollback procedures, and incident response steps.
Checks Vercel deployment list → reads recent build logs → checks for anomalies → escalates P0 infra issues to human with full context via Lark.
